# L-Space stack facts (checked 2026-10-24)

## 1. Sonos local (LAN) Control API
- Officially, Sonos says: "The Control API on the LAN is not available for wide release. Use the Control API on the cloud." Source: https://docs.sonos.com/docs/connected-home-architecture (updated 2026-04-16). The documented base URL is the cloud gateway `api.ws.sonos.com/control/api`, which uses OAuth and a developer-portal client key: https://docs.sonos.com/docs/discover, https://docs.sonos.com/docs/control, https://docs.sonos.com/reference/about-control-api
- Unofficially, `wss://<ip>:1443/websocket/api` with an `X-Sonos-Api-Key` header and a `Sec-WebSocket-Protocol` header is used by jjlawren/sonos-websocket. This is the library Home Assistant uses for audio clips. It ships a hardcoded API key: https://raw.githubusercontent.com/jjlawren/sonos-websocket/main/sonos_websocket/websocket.py , https://github.com/jjlawren/sonos-websocket . sonosify on PyPI says it uses the "local Control API WebSocket for audio clips… no API keys" in the sense that the user doesn't supply one: https://pypi.org/project/sonosify/
- Getting a key: officially, a "Control integration" key comes from the Sonos Developer Portal and is meant for the cloud: https://github.com/sonos/api-web-sample-app . I found no official way for non-partners to get a LAN key. **UNVERIFIED**.
- Certificate: players serve TLS on 1443, but no source says whether the cert is self-signed or Sonos-CA-signed. **UNVERIFIED**. The library code does connect without verifying the cert; see the source file above.
- Server-process use: the community libraries run on servers (Python/Home Assistant), so it works technically. It is not officially supported.
- Discovery: Sonos docs only describe cloud discovery (households/groups via the API). Community firewall guidance lists UDP 5353 (mDNS), UDP 1900 (SSDP), and TCP 1400/1443/3400: https://en.community.sonos.com/advanced-setups-229000/firewall-rules-6929804 . The `_sonos._tcp` service name specifically is **UNVERIFIED**. The bonob README mentions SSDP/seed-host discovery: https://github.com/simojenki/bonob

## 2. WKWebView / PWA
- WKNavigationDelegate `webView(_:didReceive:completionHandler:)` lets native code accept server-trust challenges for navigations: https://developer.apple.com/documentation/webkit/wknavigationdelegate/webview(_:didreceive:completionhandler:) . Whether that delegate fires for a JS `new WebSocket('wss://self-signed')` is **UNVERIFIED** (no primary source found). Plan on native bridging, e.g. URLSessionWebSocketTask plus a JS message handler.
- JS mDNS/SSDP: no web API for raw UDP or multicast exists in WebKit. That is my inference; I found no source confirming it. **UNVERIFIED**, but very likely "no". Native apps on iOS 14+ need the Local Network permission prompt: https://support.apple.com/en-us/102229
- PWA background audio: installed iOS PWAs pause or lose audio when backgrounded or locked. WebKit bugs from the iOS 26 era: https://bugs.webkit.org/show_bug.cgi?id=295518 , https://bugs.webkit.org/show_bug.cgi?id=291892 ; also https://stackoverflow.com/questions/60003027 . A native app needs the Audio background mode: https://developer.apple.com/documentation/avfoundation/configuring-your-app-for-media-playback

## 3. loadCloudQueue and customsd
- loadCloudQueue accepts `itemId` and `positionMillis` (optional, default 0), plus playOnCompletion and other fields: https://docs.sonos.com/reference/playbacksession-loadcloudqueue-sessionid , https://docs.sonos.com/docs/playback-objects , https://docs.sonos.com/docs/cloud-queue-play-audio . You need a playback session first (createSession/joinSession): https://docs.sonos.com/docs/playback-sessions.md
- customsd on S2: since a May 2024 S2 app update, local SMAPI services no longer work. The service must be reachable from the internet (the Sonos cloud calls it). bonob README: https://github.com/simojenki/bonob (issue #205). A Sonos community post (about 2 months old) says local services are not supported on S2, but already-configured customsd entries still work: https://en.community.sonos.com/controllers-and-music-services-228995/getlastupdate-is-not-being-called-6934458 . The official route is the Integration Sandbox: https://docs.sonos.com/docs/test-your-service
- **Implication: the SMAPI endpoint must be public HTTPS.**

## 4. Bun
- `ws` npm with `rejectUnauthorized:false` or a top-level `ca`/`cert` fails with "TLS handshake failed". Bun's shim drops the top-level TLS options. Status: reproduced, fix PR #31397 was still open on Bun 1.4.2 as of 2026-09-11. The issue is closed (dup of #29493/#22870). Workaround: pass `{ tls: { rejectUnauthorized:false, ca } }` (Bun's own shape). PEM works; pfx is broken (#42322): https://github.com/oven-sh/bun/issues/31396 . Bun's native WebSocket documents `tls` options: https://bun.sh/reference/bun/WebSocketOptions
- `node:dgram` multicast: `addMembership` exists: https://bun.com/reference/node/dgram/Socket/addMembership . A segfault in 1.2.2 was fixed (missing null check): https://github.com/oven-sh/bun/issues/17047 . Bun also has a native `Bun.udpSocket` with addMembership: https://bun.com/reference/bun/udp/Socket/addMembership . Whether multicast-dns or bonjour-service run on Bun is **UNVERIFIED**.
- `soap` (node-soap, MIT, v1.6.x, actively published): https://www.npmjs.com/package/soap . It has a server via `soap.listen(httpServer…)`. I found no Bun-specific compatibility report. **UNVERIFIED**. Bun lists node:http as fully implemented: https://bun.com/docs/runtime/nodejs-compat
- `bun build --compile` produces single binaries with a cross-compile target list that includes linux x64/arm64 for glibc and musl: https://bun.com/docs/bundler/executables . Official Docker image `oven/bun`: **UNVERIFIED** (I didn't fetch it).

## 5. Rust
- SOAP: `soap-server` is a WSDL-driven SOAP 1.1/1.2 server on axum. It is a dispatch layer only: you get raw body bytes in and return XML bytes: https://docs.rs/soap-server . Its maturity, downloads, and age are **UNVERIFIED**. The hand-rolled option is quick-xml (MIT, actively released, 0.39.x) or yaserde for serde-style XML: https://docs.rs/quick-xml/latest/quick_xml , https://docs.rs/yaserde
- WebSocket with custom TLS: tokio-tungstenite `connect_async_tls_with_config(..., Some(Connector::Rustls(Arc<ClientConfig>)))`: https://docs.rs/tokio-tungstenite/0.28.0/tokio_tungstenite/fn.connect_async_tls_with_config.html , example: https://users.rust-lang.org/t/use-tokio-tungstenite-with-rustls-instead-of-native-tls-for-secure-websockets/90130 . Self-signed certs need a custom `ServerCertVerifier` through rustls `dangerous()`: https://docs.rs/rustls/latest/rustls
- mDNS: `mdns-sd` provides a daemon thread with flume channels, is runtime-agnostic, does browse/register/resolve_hostname, and is multicast only: https://docs.rs/mdns-sd
